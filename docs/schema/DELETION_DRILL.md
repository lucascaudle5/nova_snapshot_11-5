# Layer 3 deletion drill — synthetic data only

Authority: Lucas's erasure/backup decisions, 2026-11-04; Memory and continuity #6, #10; Mind #10; Relationships #2–4, #11. Normative shapes, dependency approval, feed and backup rules are in [CONVENTIONS.md](CONVENTIONS.md); cross-room unavailable references are in [CROSS_ROOM.md](CROSS_ROOM.md). This is a numbered test **specification**, not code or evidence a drill ran. **No real data before backup, restore and this drill pass.** Mind/Relationships may begin after those same-account gates; B2 is not a prerequisite and, if later added, must enforce the same 30-day cap and pass its own drill.

1. **Establish isolation and inventory.** Use a disposable synthetic store and test clients only. Inventory every storage/read/copy path: current UI/API, typed rows/envelopes/history, sources/artifact bytes/OCR/previews, operation/retry state, search/FTS/embedding indexes, SQLite indexes/free pages/WAL/journals, logs/errors/traces, caches/offline clients, active export workers/staging, export manifests/chunks/versions, rollback copies, built-in recovery points, off-account copies and any known downloads/exports. Unknown location/expiry or an uncontrolled secret-bearing copy is a failure to prove the full promise, not an assumed clean surface. Confirm the independent erasure catalog/control authority exists for the test; do not use a list restored from the test DB.

2. **Seed distinguishable canaries and unrelated controls.** Use unique conspicuous synthetic phrases such as `NOVA_ERASE_CANARY_MIND_A` and `NOVA_ERASE_CANARY_REL_B`, plus unique synthetic dates/zone/actors/reasons/provider identities so metadata leaks are detectable too. In Mind create entries/ratings, an episode/interpretation, medication/care references and a support plan with a revealing retired step, named synthetic support person and a safe unrelated step. In Relationships create a shared conversation with the owner and two synthetic people, messages by each, a revealing preference/profile claim, draft and commitment, plus independently safe messages. Seed a separate unrelated room fact/source and known numerical control total that must survive unchanged.

3. **Seed sources and revealing copies.** Retain synthetic text, audio/image/PDF artifacts, labels/filenames, OCR/transcript/excerpts and thumbnail versions containing each canary. Reuse one original screenshot/source across a sensitive and an unrelated record to force shared-source review. Add quoting and paraphrasing annotations, an interpretation/summary, a link whose relation/role alone reveals context, a source evidence association and a safe ID-only incoming reference. Include historical/retired annotation/link/source revisions, not only current text. Create Schedule, Finances, Inventory, Body/Learning/Focus/Workshop/Music references as supported by their FKs/link registry, with a mix of safe and revealing purpose text. Do not invent invalid targets to make the test pass.

4. **Exercise history and replay identities.** Correct and deliberately revise the target, soft-delete it, restore it, and retain every revision ID. Preserve original client_op_id/digest/sequence values in a protected transient test harness for later replay assertions; never write them into a permanent post-erasure report. Create one multi-record operation containing both a selected sensitive result and a safe result. Import the same original bytes through two known provider/file aliases, retain a partially completed old import/export worker and an offline client's pending write. Confirm the baseline history/citations/FKs and partial uniqueness are valid before erasure.

5. **Create covering recoverable copies.** Produce test same-account exports/snapshots with original canaries, including an old allowed recovery point near the 30-day limit, staging/candidate chunks and object versions. If B2 exists in the test, copy them there with the original expiry. Attempt an indefinite/31-day/recopied-with-reset-expiry backup and require rejection. Record an inventory of opaque copy handles, original recovery points and enforced expiry for testing; it must not become an unbounded content archive. Cloudflare's built-in 30-day PITR/selective-scrub limitation is **from the design, not verified against Cloudflare**; the actual layer 3 integration gate must verify real platform behavior. A fake clock/unit check alone is not proof of provider expiry.

6. **Prepare and review the exact erase scope.** Request hard erasure with a fresh client_op_id. Require all target revisions/roots, known source aliases/artifacts, shared consumers, quoting/revealing dependencies and affected original operations to appear. Leave one dependent unanswered: acceptance must block with no silent redaction or retention. Exercise each explicit `erase` and `retain_nonrevealing` decision as Lucas in the synthetic scenario. Verify that another person's words and a retired support-plan step are not silently considered safe. Change a reviewed dependency before acceptance: require invalidation/re-review. Agree on a final frozen list; no quote-bearing approval transcript survives as an unreviewed new copy.

7. **Accept one logical erase and inject failures.** First test a missing/unavailable independent ID-list authority: no acceptance or unsafe service. Then persist the exact approved revision/root IDs in that authority and inject a SQLite failure after marker release/stub work: local SQL must roll back, the authoritative erasure barrier must remain, and affected content stays fenced until the same approved scope is completed. Complete one logical operation with one accepted sequence E, not one accepted operation per row. Artifact/purge failure returns visible pending/failed verification, never false local_verified. A normal successful path verifies local cleanup and returns only safe IDs/action/status fields.

8. **Inspect the exact erased-row shape.** Every selected original/correction/revision/soft tombstone/restored revision has is_erased=1, is_current=0, change_kind=erased, kind/supersedes_id/all specified times/actors/reasons/attribution/client_op_id NULL; id/root_id/original op_seq survive, with erasure_op_seq=E. Root membership still resolves and every member is covered. Every original typed table retains exactly one same-id stub with only id/is_current/is_erased non-NULL; all domain fields, including old NN columns, are NULL. Deliberately try a stub retaining a name/amount/status/FK or a live row missing an NN-live field: the shared two-state CHECK must reject it. Try mismatched flags: the deferred triple FK must fail at commit. Run FK integrity and current partial-index checks; safe incoming FKs still resolve to stubs and safe unrelated totals stay unchanged, while any contribution requiring erased values is explicitly unavailable.

9. **Inspect all reading and evidence surfaces.** Current reads omit erased facts; history/as-known/as-effective/search/Inspect/Overview/citation/navigation return erased/unavailable and never recover the old text or metadata. Retained safe evidence rows show **evidence unavailable**, not a fictitious source. Shared original bytes/extractions/previews are absent locally even though approved safe consumer rows survive. Revealing annotations/links and all their versions are stubs; safe reviewed ones do not reconstruct the secret. Support plans with erased content visibly report incomplete/unavailable and trigger no automatic action. Test a read/export snapshot opened before E: after the erasure fence it cannot transmit its stale secret-bearing page or finalize an unqualified clean export.

10. **Inspect operations, storage and leakage.** Affected original operations, including the mixed operation, are sealed with digest/time NULL; erase operation also has no digest/time, names, source URI, original kind or request copy. Its manifest contains only allowed opaque IDs/action codes; its source tokens contain no raw provider ID/content hash/secret key. Check errors/logs/traces/old receipts and client caches for canaries and sensitive metadata, not just the main table. Verify local artifact deletion and physical DB/WAL/free-page/index/FTS/vector/cache cleanup using the storage implementation's appropriate recovery tools. SQL NULL alone or a text-only grep is insufficient to certify local byte erasure.

11. **Exercise the change feed and client purge.** Fetch operations since before E and require the one safe erase receipt. Fetch records-changed since before E for **every kind**, including a kind with no original target: all receive opaque erasure notices through erasure_op_seq, without revealing former kind. Page inside E, reconnect an offline client and repeat pages/notices: no omission, false sequence advance or missed invalidation from deduplicating by record ID alone. Purge all cached revisions, old receipts, previews, excerpt/derived copies and pending writes. Unknown/offline client cleanup remains unverified until it reconnects/acknowledges; do not claim remote recall.

12. **Attack retry and re-ingestion paths.** Retry each original client_op_id with its old body, a changed body and an independent fresh client ID pointing at the erased root; no source or typed content returns. Retry the erase: same E, scope and safe receipt, no new accepted sequence/work/copy. Attempt ordinary correction, soft restore and direct stub refill: reject. Re-import original bytes under the same and a new filename/provider alias; known identity/byte suppression must block before any source/artifact/log payload is created. Complete the old import/worker/offline write: finalization is refused and staging bytes purged. Try an unavailable/rotated-away verifier key: fail closed, not silently bypass. Include a transformed screenshot/rewritten text to document the **semantic matching limit**; unknown transformations must not be advertised as guaranteed suppressed, and suspected matches require review rather than automatic revival of an old root.

13. **Check ordinary expiry versus urgent scrub.** On normal erase, covering export objects remain recoverable only until their original permitted expiry: do not rewrite every export or falsely mark backup_state verified. Built-in PITR may also retain the canary until age-out; this is an expected **disclosed** expiry_pending state during the window, not an immediate-all-copies promise. Request urgent scrub separately: covering export objects/versions/chunks are deleted and a fresh consistent clean export is made; verify the canary is absent from it. Built-in recovery remains outside urgent scrub's reach. A hidden version, new expiry on a copied old snapshot or an export-before-erase archive fails.

14. **Restore the oldest allowed pre-erasure backup.** In a new quarantined test store with no content preview/indexing/import/dispatch, restore that raw backup, even if it still contains the canary in permitted backup storage. Fetch the current independent ID-only list, not the backup's list. Restore with stale/missing authority or keys: remain quarantined. With valid authority, match both record and root IDs, include restored revisions absent from the original version list, stub/re-erase everything before use, carry forward operation seals/tokens, and allocate a fresh replay erasure sequence above the authoritative high-water if E is absent from the backup. Preserve the list across repeated restores. A newly discovered revealing dependent requires individual confirmation before release; do not silently invent or discard content. Only then rebuild clean indexes, use a new store-history incarnation and force client resync. The original retry/import attempts must remain blocked after restore too.

15. **Prove the 30-day every-copy bound.** Inspect **all** restorable copies at expiry: PITR recovery range, export/rollback/staging/object versions, off-account/B2 and known other copies. Demonstrate actual enforced expiry or unrecoverability by no later than erase+30 days, with no recopy/hold exception; retain truthful pending status until demonstrated. The provider gate requires real evidence, not a claimed nonexistent service. Reattempt restore of an expired covering snapshot: reject/unrecoverable. Current canonical erasure IDs remain despite backup expiry; default retention is indefinite, and dropping an ID merely because 30 days passed fails. No erase operation generated an archive; any hypothetical later export-before-erase feature is out of this adopted design.

16. **Record pass/fail without preserving the secret.** The drill report contains only synthetic scenario labels, opaque test handles/sequences, checks/statuses, platform verification evidence and documented limits; destroy secret-bearing transient fixture/retry payload copies under the same policy. Fail on any content/identifying metadata in an active/unaccounted copy, missing review, FK/stub mismatch, stale read exposure, false success, revived old ID, known alias re-import, unexpected sequence reuse, unbounded copy or pre-replay restore use. Pending permitted recovery copies must stay explicitly expiry_pending until expiry; the test must prove their bound, not pretend they were immediately scrubbed.

17. **Release-gate conclusion.** Layer 3 passes only when backup and quarantined restore work, this full drill has actual evidence for each implemented storage surface, every-copy lifetime is enforced, and the documented scope/semantic/offline-client limits are accurately reported. Spec-only SQLite checks do **not** pass this gate. Any storage surface introduced later, including B2, needs the applicable drill before real content relies on it. No real Mind/Relationships data is required to run this test.
